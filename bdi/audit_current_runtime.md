## What Is Generated By Bash

`bdi/run_agent_for_scenario.sh` creates:

```text
bdi/generated/<scenario>_agent.asl
bdi/generated/<scenario>.mas2j
```

It prepends the static scenario belief file from:

```text
telemetry/generated_beliefs/<scenario>.asl
```

to:

```text
bdi/cicd_agent.asl
```

When the runner is called without `--jason`, it does not run Jason. It calls the shell function `print_modeled_trace()`.

That Bash function checks belief lines with `grep` and prints:

```text
Goal: ...
Action: ...
Result: ...
Decision: ...
```

Therefore, the normal `Decision:` output is Bash-generated modeled output.

## What Is Generated By Python

`experiments/compile_results.py` calls:

```text
bdi/run_agent_for_scenario.sh <scenario>
```

without `--jason`.

It then parses the modeled trace:

```python
line.split("Decision:", 1)[1].strip()
```

and records the last parsed decision as `bdi_decision`.

`experiments/real_telemetry_runner.py` also calls:

```text
bdi/run_agent_for_scenario.sh <scenario>
```

without `--jason`.

It runs the real shell CI/CD action sequence itself, writes static live beliefs, parses the modeled BDI trace, and if the parsed decision is `rollback_production`, it invokes:

```text
cicd/actions/rollback.sh production
```

from Python.

Therefore, current experiment results are assembled by Python using Bash-modeled BDI decision text.

## What Is Generated By Jason

The repository does contain a Jason MAS definition:

```text
bdi/project.mas2j
```

and AgentSpeak source:

```text
bdi/cicd_agent.asl
```

The runner has a `--jason` branch that attempts to launch Jason. On this machine, Jason CLI 3.3.0 is installed.

However, during this audit, the Jason execution path did not emit the expected AgentSpeak `.print(...)` trace to the captured console. The only observed output from the `--jason` run was the runner's own launch message.

So the safe conclusion is:

- Jason is installed.
- The repository can generate Jason project files.
- The runner can attempt to launch Jason.
- The current audited run did not provide visible evidence that Jason selected plans or emitted the decision trace.
- The default and experiment paths do not rely on Jason.

## Answers To The Core Questions

### Is Jason actually launched?

Not in the default path. The default `bdi/run_agent_for_scenario.sh success_stable` path does not launch Jason.

With `--jason`, the script attempts to launch Jason and the local Jason CLI exists, but the audited run produced no visible AgentSpeak trace.

### Does Jason currently make the experiment decisions?

No evidence in the default path. The decisions consumed by experiment scripts are printed by Bash and parsed by Python.

### Are beliefs loaded dynamically?

No. Current scenario beliefs are static `.asl` facts generated before runtime and prepended to the generated agent file.

### Does Jason invoke CI/CD shell actions?

No. `bdi/cicd_agent.asl` prints symbolic action names such as `Action: build(candidate)`, but it does not call `cicd/actions/*.sh`.

In real-telemetry experiments, Python invokes the shell actions directly.

### Is there a Jason-controlled closed loop?

No. The current repository does not yet demonstrate:

```text
perceive -> update belief -> select plan/intention -> act -> environment changes -> perceive again
```

inside a persistent running Jason agent.

## Current Value

The current implementation is still useful because it has:

- a clear shell action interface;
- a real local payment service;
- Prometheus metrics;
- telemetry adapter;
- belief mapper;
- Jason/AgentSpeak plan model;
- scenario and experiment scaffolding.

The gap is specifically the runtime BDI control layer.

## Recommended Next Implementation Step

The next step should be the smallest real Jason runtime milestone:

1. Create a persistent `deployment_agent.asl`.
2. Run it directly from `bdi/project.mas2j`.
3. Add a Jason environment or CArtAgO artifact.
4. Expose action-result perceptions such as `status(build, passed)`.
5. Let Jason invoke existing shell actions:

```text
cicd/actions/build.sh candidate
cicd/actions/test.sh candidate
cicd/actions/security_scan.sh candidate
cicd/actions/deploy.sh staging candidate
cicd/actions/health_check.sh staging
cicd/actions/deploy.sh production candidate
cicd/actions/health_check.sh production
cicd/actions/rollback.sh production
```

6. Only after that, add periodic telemetry perception updates from Prometheus.

This preserves the working telemetry and action layers while closing the main research gap: Jason must become the visible, persistent decision-making controller.
